# 収益診断（Revenue Diagnostic）Web実装 要件定義書

最終更新: 2026-06-10
対象サイト: Consilegy（WordPress / CORESERVER）

---

## 1. 背景・目的

### 背景
- Consilegyとして「直接客が・正規料金で・収益構造の仕事を発注した」案件は現状ゼロ。
- 直接客を獲得する導線（front door）が存在しない。問い合わせはDM頼みで、現在は止まっている。
- 一方、ニュースレター（日本語1,000人／英語850人、読者の61%がCXO・VP・シニア層）という温かい資産がある。

### 目的
Webに「収益診断」を実装し、**ニュースレター／LinkedInプロフィール流入を、有料診断 → 受注へつなぐ front door** にする。
同時に以下を兼ねる:
1. **リード獲得**（メールアドレス・課題情報の取得）
2. **緊急性の創出**（漏れの定量化で「直したい」を引き出す）
3. **プロダクトの市場調査**（共通の漏れパターンを蓄積 → 将来のAIダッシュボード/CRMの種）

---

## 2. ターゲット

| 項目 | 内容 |
|---|---|
| 主対象 | 日本のB2B中堅企業（おおむね50〜300名）の経営者／営業・マーケ責任者 |
| 入口の痛み | 「リードはあるのに商談・受注につながらない」「営業が属人化して売上が読めない」「マーケに投資しても成果が見えない」 |
| 流入経路 | LinkedInプロフィール、ニュースレター、投稿、紹介 |
| デバイス | **モバイル比率が高い前提**（LinkedIn流入はスマホ中心）→ モバイルファースト必須 |

---

## 3. スコープ

### Phase 1（MVP・今回の対象）
- セルフ収益診断（Web診断フォーム）
- スコアリングと結果表示（収益漏れマップ）
- リード獲得（メール取得・同意）
- 有料「収益診断」予約／問い合わせへの導線
- 計測（GA4イベント）

### Phase 1でやらないこと
- 結果レポートのPDF自動生成（当面は有人作成でOK）
- 決済機能（有料診断の決済は手動・請求書でOK）
- AIダッシュボード／CRMプロダクト連携
- 多言語（まず日本語のみ。英語は Phase 2）

### Phase 2（将来）
- 結果のPDF自動生成・自動送付
- HubSpot自動連携（リード自動登録・スコア連携）
- 決済導入
- 英語版

## 4. 画面構成・フロー

```
[1] 診断LP（紹介ページ）
      ↓ 「無料で診断する」
[2] 診断フォーム（6カテゴリ × 設問）
      ↓ 全問回答
[3] メール取得フォーム（氏名・会社・役職・メール・同意）
      ↓ 送信
[4] 結果ページ（収益漏れマップ + スコア + 示唆 + CTA）
      ↓ 「収益診断を予約」 / 「相談する」
[5] 予約 or 問い合わせ（Calendly等 / 問い合わせフォーム / DM導線）
```

メール取得は **[2]の後・結果[4]の前**（結果を見る条件としてメール取得）。
※ハードルを下げたい場合は「結果は見せて、詳細レポートはメールで」という分岐も可（Phase 2で検討）。

## 5. 機能要件

### 5.1 診断ロジック
- カテゴリ数: **6**（後述）
- 各カテゴリ設問数: **2問**（計12問）
- 回答形式: 単一選択（3択）
- 配点: 各選択肢に **漏れリスク点 0 / 1 / 2**（高いほど漏れている）
- カテゴリスコア: 2問合計（0〜4点）
- 信号判定: `0–1=🟢 健全` / `2–3=🟡 注意` / `4=🔴 漏れ`
- 総合スコア: 全12問合計（0〜24点）。低いほど健全。

### 5.2 結果表示（収益漏れマップ）
- 6カテゴリの信号（🔴🟡🟢）を一覧表示
- 総合スコアと「健全度」帯（後述のスコア帯コピー）
- 漏れている上位カテゴリの**示唆コメント**（カテゴリ別固定文を出し分け）
- 「最初の一手」1つ（カテゴリ別固定文）
- CTA（有料診断予約／相談）

### 5.3 リード獲得
- 取得項目: 氏名／会社名／役職／メールアドレス（任意: 従業員規模・業種）
- プライバシー同意チェック必須（取得目的明示）
- 送信先: **MVPは「管理者へメール通知＋スプレッドシート蓄積」で可**（HubSpot自動連携はPhase 2）

### 5.4 CTA
- 結果ページに常時表示のCTAボタン
- 主CTA: 「収益診断（有料・90分）を予約する」→ Calendly等
- 副CTA: 「まず相談する」→ 問い合わせフォーム or LinkedIn DM

## 6. コンテンツ要件（実装に必要な中身）

### 6.1 診断カテゴリと設問

> 配点表記: 選択肢の後ろの `[n]` が漏れリスク点。

**① マーケ→営業の受け渡し**
- Q1.「"商談化できるリード"の条件を、営業とマーケが同じ言葉で説明できますか？」
  - はっきり言語化され、両部門で一致 `[0]`
  - なんとなく共有しているが曖昧 `[1]`
  - 部門ごとにバラバラ／決まっていない `[2]`
- Q2.「マーケが渡したリードのうち、営業が"対応に値する"と判断する割合は？」
  - 把握しており、おおむね高い `[0]`
  - 感覚的にしか分からない `[1]`
  - 渡したきり追えていない `[2]`

**② 営業の属人化**
- Q1.「トップ営業が抜けたら、来期の売上予測はどれくらいブレますか？」
  - ほぼ影響しない（仕組み化されている）`[0]`
  - そこそこ影響する `[1]`
  - 大きく落ちる／読めなくなる `[2]`
- Q2.「商談化や受注の判断基準は、個人の勘ですか、組織の基準ですか？」
  - 組織で標準化された基準がある `[0]`
  - 一部だけルール化 `[1]`
  - ほぼ個人の勘 `[2]`

**③ 商談ステージのズレ**
- Q1.「CRMのステージは何を表していますか？」
  - 顧客の購買の進捗を表している `[0]`
  - 自社の活動を表している `[1]`
  - 入力ルールが曖昧／機能していない `[2]`
- Q2.「売上予測（forecast）は、どれくらい当たりますか？」
  - おおむね当たる `[0]`
  - 月によってブレる `[1]`
  - 毎回ズレる `[2]`

**④ データの分断**
- Q1.「経営会議の数字は、どう作っていますか？」
  - 一元化され、ほぼ自動 `[0]`
  - 複数ツールから一部手作業 `[1]`
  - 毎回、人が手集計している `[2]`
- Q2.「部門間で同じ指標の数字が食い違うことは？」
  - ほぼない `[0]`
  - たまにある `[1]`
  - よくある／どれが正か分からない `[2]`

**⑤ ツールの非定着**
- Q1.「現場は毎日CRM/SFAを開いて使っていますか？」
  - 日常的に使っている `[0]`
  - 一部のメンバーだけ `[1]`
  - 結局Excel/スプレッドシートに戻っている `[2]`
- Q2.「導入したツール（CRM/MA等）は、期待した役割を果たしていますか？」
  - 果たしている `[0]`
  - 一部だけ `[1]`
  - ほぼ使われていない／形骸化 `[2]`

**⑥ 受注後の継続・拡大**
- Q1.「受注後、誰がいつアップセル/継続の判断をしていますか？」
  - 役割と時点が設計されている `[0]`
  - 担当者の裁量任せ `[1]`
  - 特に決まっていない `[2]`
- Q2.「営業→CS（カスタマーサクセス）の引き継ぎ設計はありますか？」
  - ある `[0]`
  - 口頭・属人的 `[1]`
  - ない／取って終わり `[2]`

### 6.2 総合スコア帯コピー（結果ページ見出し）

| 総合点 | 帯 | 見出しコピー（例） |
|---|---|---|
| 0–6 | 健全 | 「収益の流れは概ね設計されています。伸ばす余地は"拡大"側にあります」 |
| 7–14 | 注意 | 「いくつかの境目で、売上が静かに漏れています。今が直し時です」 |
| 15–24 | 要改善 | 「複数の境目で大きく漏れています。ツールではなく、構造の問題です」 |

### 6.3 カテゴリ別 示唆コメント＋最初の一手（🔴/🟡時に表示）

| カテゴリ | 示唆コメント | 最初の一手 |
|---|---|---|
| ① 受け渡し | リードはあっても、定義のズレで商談前に消えています | 営業とマーケで「商談化リードの条件」を1枚に言語化する |
| ② 属人化 | 売上が人に依存し、予測が立ちません | トップ営業の「判断基準」を3つ言語化して共有する |
| ③ ステージ | CRMが活動の記録止まりで、購買進捗を測れていません | ステージ定義を「顧客の状態」で再定義する |
| ④ 分断 | 数字がバラバラで、経営判断が遅れています | 経営会議で見る指標を1つの正データに統一する |
| ⑤ 非定着 | ツールが現場の日常になっていません | 現場が毎日開く理由（1機能）に絞って運用を立て直す |
| ⑥ 継続 | 受注後の拡大が設計されず、LTVが伸びていません | 受注→CSの引き継ぎチェックリストを作る |

### 6.4 LPコピー骨子（[1]診断LP）
- 見出し: 「あなたの会社は、どこで売上が漏れているか？」
- サブ: 「マーケ・営業・CSの"境目"を6つの観点で1分診断。無料」
- 共感: 3つの痛み（リード→商談／属人化／マーケ成果）
- 中身説明: 6カテゴリの信号マップが出る
- 信頼: 支援40社／レベニューアーキテクチャ
- CTA: 「無料で診断する（約1分）」

### 6.5 CTAコピー（[4]結果ページ）
- 主: 「この漏れを"直す"なら｜収益診断（90分）を予約する」
- 補足: 「正式な収益診断レポート付き。プロジェクトに進む場合は診断料を全額充当します」
- 副: 「まずは相談する」

## 7. 非機能要件

| 項目 | 要件 |
|---|---|
| モバイル対応 | 必須。スマホで1問ずつ快適に回答できるUI |
| 表示速度 | 診断開始までの待ち時間最小化（重いプラグイン回避） |
| 個人情報 | プライバシーポリシー整備、取得目的の明示、同意チェック必須 |
| アクセシビリティ | 文字コントラスト・タップ領域の確保 |
| ブランド | バナー世界観（収益を設計する／Revenue Architecture）と整合 |

## 8. 計測・KPI

### GA4で計測するイベント
- `diagnostic_start`（診断開始）
- `diagnostic_complete`（全問回答）
- `lead_submit`（メール取得）
- `result_view`（結果表示）
- `cta_book_click`（有料診断予約クリック）
- `cta_contact_click`（相談クリック）

### KPI
| 指標 | 定義 |
|---|---|
| 診断開始数 | LP→開始 |
| 完了率 | 完了 ÷ 開始 |
| メール取得率 | lead_submit ÷ 完了 |
| 予約率 | 予約 ÷ メール取得 |
| 受注率 | 受注 ÷ 予約 |

## 9. 技術前提・実装方針

| 項目 | 内容 |
|---|---|
| CMS | WordPress（CORESERVER） |
| 診断フォーム | クイズ/フォーム系プラグイン（条件分岐・スコア集計対応）または軽量カスタム実装 |
| データ蓄積 | MVP: フォーム→管理者メール通知＋スプレッドシート。Phase 2: HubSpot連携 |
| 予約 | Calendly等の外部予約ツール埋め込み |
| 既存CRM | HubSpot（Phase 2で連携） |
| 制作ルール | CLAUDE.md準拠（本番更新前にDBバックアップ、テストページ先行、page builder構造を確認してから反映） |

## 10. 実装フェーズ

1. **MVP**: LP＋診断フォーム＋スコア＋結果ページ＋メール取得＋予約導線＋GA4
2. 数十件運用 → 設問・結果コピー・CTA改善
3. **Phase 2**: PDF自動生成、HubSpot自動連携、決済、英語版
4. 蓄積データから共通の漏れパターンを抽出 → プロダクト（AIダッシュボード/CRM）の要件へ
