## 2. カテゴリ別 相対定量コピー（`quant`）

各カテゴリに `quant: string` を追加。**🔴/🟡のとき** insight の直後に1行表示。
※すべて「同規模・同型の会社では〜が典型」という**相対フレーム**。その会社固有の実数ではない（精密試算はPhase 2/有料診断側でやる）。断定を避けるため語尾は「典型」「目安」で締める。

| カテゴリ | quant コピー |
|---|---|
| ① 受け渡し | マーケが渡したリードの **3〜5割** が、商談化の手前で「対応に値しない」と判断されて消えるのが典型です。広告費が商談の一歩手前で蒸発している状態です。 |
| ② 属人化 | 売上が上位2〜3名に集中している組織では、**その1人の離職が翌期forecastを最も大きく揺らす要因**になります。営業リスクが実質的に財務リスクです。 |
| ③ ステージ | ステージが「自社の活動」を表している会社のforecastは、月次で **±20〜30%** ぶれるのが目安です。打ち手が常に後手に回ります。 |
| ④ データ分断 | 数字を手集計している組織は、**経営会議の準備だけで毎月数十時間**を溶かしています。しかも「どれが正か」の議論で意思決定が遅れます。 |
| ⑤ 非定着 | 使われないCRMはデータの鮮度・網羅性が落ち、「**使えないから使わない**」の悪循環に入ります。投資したツール費がそのまま埋没コストになります。 |
| ⑥ 継続・拡大 | 新規獲得は既存拡大の **約5倍** のコストがかかります。出口（継続・拡大）の設計不在は、**最も高くつく漏れ**です。 |

## 3. 掛け合わせパターン（`PATTERNS`）★コア

「どのカテゴリが赤か」ではなく「**赤がどこに重なっているか**」で型を出す。これがレベニューアーキテクトの差別化（境目の連鎖を読む）。

### 表示ルール
- 赤（score=4）の集合 `red` を作り、下記を**上から評価して最初に一致した1本**を表示。
- 赤が1つ以下のときはパターン非表示（健全〜注意の軽い結果）。
- カテゴリ記号: ①H=受け渡し / ②D=属人化 / ③S=ステージ / ④L=データ分断 / ⑤A=非定着 / ⑥E=継続・拡大。

### パターン定義（優先順）

**P1 構造崩れ** — 条件: `red.length >= 4`
> 見出し: **これはツールの問題ではなく、収益の設計そのものの問題です**
> 本文: 複数の境目で同時に漏れているとき、原因は個別の機能やツールではありません。収益の流れ（リード→商談→受注→拡大）が一度も設計されていない状態です。手当てを足すほど複雑になります。一度、流れ全体を引き直す段階にあります。

**P2 両端型（入口×出口）** — 条件: `H∈red && E∈red`
> 見出し: **中間（営業）は動いているのに、入口と出口で失っています**
> 本文: 現場の営業力で受注は取れています。一方で、リードの入口と受注後の拡大が設計されていないため、努力が「一度きりの受注」で終わっています。獲得コストが高止まりし、LTVも伸びない——最も入れ替わりの激しい二重の漏れです。

**P3 forecast不全（属人化×ステージ）** — 条件: `D∈red && S∈red`
> 見出し: **売上が「読めない」のは、この2つが重なっているからです**
> 本文: 売上が個人の勘に依存し、CRMのステージも購買進捗を表していません。この2つが重なると、forecastは**構造的に**当たりません。気合や精度向上では直らない領域で、経営の意思決定が常に後手に回ります。

**P4 可視化崩れ（分断×非定着）** — 条件: `L∈red && A∈red`
> 見出し: **数字が「作るもの」になっていて、土台が無い状態です**
> 本文: ツールが現場に根付かず、経営の数字は毎回手集計。これではKPI管理も投資判断も、土台のないまま回しています。新しい施策の良し悪しを測れないため、改善のループが回りません。

**P5 入口の二重漏れ（受け渡し×属人化）** — 条件: `H∈red && D∈red`
> 見出し: **入口で二重に失っています**
> 本文: マーケが渡したリードが定義のズレで消え、拾えるかどうかも営業個人の勘次第。せっかくの母数を、商談に入る前に二段階で削っています。マーケ投資のROIが見えなくなる典型です。

**P6 営業エンジン不全** — 条件: `(D∈red || S∈red)`（P3未該当）
> 見出し: **受注はできても、再現できる形になっていません**
> 本文: 数字は取れていますが、「誰がやっても同じ結果」にはなっていません。スケールの天井はここです。人を増やしても売上が比例しないなら、原因はこの境目です。

**P7 入口集中** — 条件: 最悪カテゴリが H かつ `H∈red`
> 見出し: **一番もったいない漏れが、入口に出ています**
> 本文: 集めたリードを、商談に入る前の「定義のズレ」で捨てています。新規獲得を増やす前に、ここを直すのが最も費用対効果が高い一手です。

**P8 出口集中** — 条件: 最悪カテゴリが E かつ `E∈red`
> 見出し: **獲得は機能しています。伸びしろは"既存の拡大"側です**
> 本文: 入口は回っているぶん、いま取りこぼしているのは既存顧客のLTVです。新規より安く、確度の高い売上が、出口の設計不在で抜けています。

**P9 フォールバック** — 条件: `red.length >= 2`（上記すべて未該当）
> 見出し: **2つの境目が同時に漏れています：{赤カテゴリ名1}と{赤カテゴリ名2}**
> 本文: それぞれ単独でも売上を削りますが、重なると影響が掛け算になります。まずは上位の{最悪カテゴリ名}から手をつけるのが順番です。

## 4. 実装メモ（diagnostic-data.ts への落とし方）

```ts
// DiagnosticCategory に追加
quant: string; // 🔴/🟡時に insight の直後に表示

// 新規: パターン判定
export interface LeakPattern {
  id: string;
  headline: string;
  body: string;
}

// red: 赤(score===4)カテゴリの id 配列, worstId: 最高スコアのカテゴリ id
export function patternOf(
  red: string[],
  worstId: string,
  categoryName: (id: string) => string,
): LeakPattern | null {
  const has = (id: string) => red.includes(id);
  if (red.length >= 4) return P1;
  if (has('handoff') && has('expansion')) return P2;
  if (has('dependence') && has('stages')) return P3;
  if (has('silos') && has('adoption')) return P4;
  if (has('handoff') && has('dependence')) return P5;
  if (has('dependence') || has('stages')) return P6;
  if (worstId === 'handoff' && has('handoff')) return P7;
  if (worstId === 'expansion' && has('expansion')) return P8;
  if (red.length >= 2) return P9(red, worstId, categoryName); // 名前を差し込む
  return null; // 赤0〜1 → パターン非表示
}
```

- 表示は **パターン1本**まで（情報過多回避・モバイル前提）。
- en版（`diagnostic-data.en.ts`）にも同じ構造で英訳を入れる（Phase 2 / 英語投稿導線と整合）。
- GA4: パターンIDを `result_view` のパラメータに乗せると、**どの漏れ型が多いか**＝プロダクト（AIダッシュボード）の種データになる（要件定義 目的③）。
