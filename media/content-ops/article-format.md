# 記事テンプレートと執筆フォーマット

media.consilegy.com 運用規格 / 2026年7月20日

---

## 使い方

テンプレートは2種類だけです。増やさないでください。判断に迷う項目が増えると、日次運用が止まります。

- **テンプレートA: 正典** — 月1〜2本。被引用を取りにいく記事
- **テンプレートB: 実務ノート** — 日次。一次情報を記録する記事

後半に、私（Claude）がベースを作り、Seikoさんが仕上げる際の**分業フォーマット**を置いています。ここが日次運用の生産性を決める部分です。

---

# テンプレートA: 正典

## 骨格

```
[title タグ] 50〜60字。主要キーワードは先頭35字以内
[meta description] 120字。何が書いてあるかを言い切る

H1: （titleとほぼ同じ。完全一致でなくてよい）

── 冒頭ブロック ──────────────────────
【定義文 / 結論】100〜120字
　単独で抜き出して意味が通る一文にする。
　「〇〇とは、△△である。」の形を基本にする。
　ここが曖昧だと、AI検索は競合ページに移ります。

【この記事で分かること】箇条書き3〜4行

【著者の立場】1〜2行
　例:「HubSpotとSalesforceの実装を8年、日本企業と
　　　海外SaaSの双方で担当してきた立場から書きます。」
──────────────────────────────────

[目次] 自動生成

H2: セクション1
　└ 冒頭100字で、このセクションの結論を先に書く
　└ その後に根拠・具体例・数字
　└ 単独で読んで意味が通ること（AIは1セクションだけ読むことがある）

H2: セクション2
　（以下同様。H2は5〜8本）

H2: 図解
　オリジナル図を最低1枚。図には必ずキャプションで
　説明文を付ける（AIは画像を読まないが、キャプションは読む）

H2: よくある質問
　H3で質問文、直下に100字前後で回答。3〜5問
　構造化データ FAQPage を当てる

── 末尾ブロック ──────────────────────
【関連する正典】内部リンク2〜3本
【根拠にした実務ノート】内部リンク3本以上
【著者ボックス】顔写真＋3行＋/about/へのリンク
【公開日 / 最終更新日】
【CTA】収益構造の相談をする
──────────────────────────────────
```

## 正典の必須要件

一つでも欠けたら公開しない、という基準です。

- [ ] 冒頭100字が、単独で引用できる定義文または結論になっている
- [ ] **数字が5個以上入っている**（自社の実務から出た数字を優先。他社調査の引用は最小限に）
- [ ] オリジナルの図が1枚以上ある
- [ ] 具体的な固有名詞が入っている（「あるツール」ではなく「HubSpot」、「近年」ではなく「2024年以降」）
- [ ] 代名詞で受けていない箇所がある(「その会社」「これ」を主語にしない)
- [ ] 実務ノートを3本以上、根拠として引用している
- [ ] FAQ が3問以上ある
- [ ] 各H2セクションが、単独で読んで意味が通る

## 数字の扱い（重要）

生成AIに引用される要因として、統計の有無が最も効きます。ただし**架空の数字は絶対に書かないでください。** 一度でもやると、この事業の土台が崩れます。

書ける数字は3種類あります。

1. **自社の実務から出た数字** — 「これまで担当した実装12件のうち、9件で最初に壊れたのは商談ステージの定義だった」。これが最強です。守秘に触れない粒度に丸めて使います。
2. **一次調査の数字** — 秋以降。ここが本命
3. **他社の公開調査** — 出典とリンクを必ず本文中に明記。これに依存している限り、立場は解説者のままです

数字が必要なのに手元にない箇所は、原稿中に `【要数値: ◯◯の実績件数】` と書いて残してください。私が勝手に埋めることはしません。

# テンプレートB: 実務ノート

## 骨格

```
[title] 30〜45字。具体的な事象で書く
　良い例:「商談ステージを7段階にしたら、
　　　　　入力率が3週間で落ちた」
　悪い例:「営業プロセス設計のポイント」

H1: （titleと同じ）

── 冒頭3行 ──────────────────────
何が起きたか。状況と結論を先に書く。
背景説明から始めない。
──────────────────────────────

H2: 状況
　いつ、どんな会社で、何をしようとしていたか
　（守秘のため業種と規模感まで。社名は出さない）
　150〜300字

H2: 何を判断したか
　どう考えて、何を選んだか。選ばなかった案も書く
　300〜500字

H2: 結果と、そこから言えること
　効いたこと、効かなかったこと。
　一般化できる原則を**1つだけ**取り出す
　200〜400字

── 末尾 ────────────────────────
【関連】正典への内部リンク 最低1本
【著者ボックス】
【CTA】ニュースレター登録
──────────────────────────────
```

## 実務ノートの必須要件

- [ ] 800〜1,200字（超えそうなら、それは正典の材料。ノートでは書かない）
- [ ] タイトルが具体的な事象を指している
- [ ] 冒頭3行で結論が分かる
- [ ] **一般化できる原則が1つだけ**書かれている（2つ以上書くと薄まる）
- [ ] 正典への内部リンクが本文中にある
- [ ] 守秘に触れていない（社名、特定できる数字、担当者名）

## 実務ノートで書いてはいけないもの

日次運用が崩れる典型がここです。

- **一般論**: 「営業とマーケの連携が重要です」。誰でも書ける記事は、書く意味がありません
- **ニュース解説**: 他社の発表や記事へのコメント。一次情報になりません
- **ツールの使い方**: 公式ドキュメントに書いてあることの言い換え
- **その日書くことがないから書いた記事**: 書くことがない日は、**過去の案件から1つ掘り出す**。それでもなければ休む。空の記事を出すより休む方が資産が守られます

**在庫があれば、この問題は起きません。**（→ 90日トピック在庫リストを参照）

# 分業フォーマット（日次運用の中核）

日次で回すうえで最大のコストは執筆ではなく、「今日何を書くか考える時間」と「書き出すまでの立ち上がり」です。ここを構造で消します。

## 私（Claude）が出すもの

実務ノート1本につき、次の形式で出します。Seikoさんは**上書きする前提**で受け取ってください。

```markdown
## タイトル案（3つ）
1. ...
2. ...
3. ...

## 冒頭3行（ドラフト）
...

## 構成
### 状況
- 【Seiko記入】いつ / 業種 / 規模 / 何をしようとしていたか
- 想定される論点: ...

### 何を判断したか
- 【Seiko記入】実際の判断
- 一般に取られる選択肢: A / B / C
- それぞれの詰まりどころ: ...

### 結果と、そこから言えること
- 【Seiko記入】実際に起きたこと
- 一般化の候補: ...

## 内部リンク先
- 正典◯「...」の第◯章へ

## 画像の指示（Recraft / ChatGPT / Claude 用プロンプト）
「...」

## 想定文字数: 約1,000字
```

**【Seiko記入】の箇所は私が埋めません。** ここが一次情報であり、この記事の価値のすべてだからです。私が埋めた瞬間に、この記事はAIが書ける記事に落ちます。

## Seikoさんの作業（目標45分）

1. **10分**: 【Seiko記入】を埋める。箇条書きで構わない。文章にしなくていい
2. **20分**: 全体を自分の言葉で書き直す。私のドラフト文はほぼ捨てる前提。私の役割は構成と論点の提示であって、文章の提供ではありません
3. **10分**: 画像生成（プロンプトは私が用意）
4. **5分**: チェックリストを通して公開

45分を超え始めたら、構成の粒度が合っていない合図です。その旨を伝えてください。次から調整します。

## 週次のリズム

日次を「毎日ゼロから」でやると折れます。**週1回まとめて仕込み、日次で出す**方が持続します。

| | 作業 | 所要 |
|---|---|---|
| 月曜 朝 | 私が今週5本分のベースを一括で出す | Seiko側 0分 |
| 月曜 | 5本分の【Seiko記入】を一気に埋める | 50分 |
| 火〜金 | 1日1本、書き直して公開 | 30分/日 |
| 金曜 | 翌週のテーマを5つ指定して私に渡す | 10分 |
| 隔週 土 | 正典の執筆に3時間まとめて充てる | 3時間 |

週あたり約4時間。月16時間。日次を毎日その場でやる場合（月25〜30時間）より、4割ほど圧縮できます。

# 文体規約

正典・実務ノート共通です。

- 敬語。落ち着いた、知的なトーン
- **結論から書く。** 前置き、背景説明からの入りを禁止する
- **エムダッシュを使わない**
- カタカナの専門語は、日本語で言えるなら日本語にする。「ナーチャリング」→「見込み客を育てる」、「ステークホルダー」→「関係者」
- 一文に横文字が3つ以上並んだら書き直す
- 製品名（HubSpot、Salesforce、freee）はそのまま使う
- 略語は初出で一言かみ砕く
- 「〜かもしれません」「〜と言えるでしょう」で逃げない。立場を取る
- 「いかがでしたか」「参考になれば幸いです」を書かない
- 一文ごとに「削っても意味が通るか」を問う。通るなら削る

# 画像の規約

図解が正典の差別化点になります。ここは手を抜かないでください。

**正典**

- オリジナルの構造図を最低1枚。ボウタイ、プロセス図、階層図など
- 図の中の文字は日本語。英語のフレーム図をそのまま載せない
- 配色は2〜3色に絞る。Consilegyのブランドカラーを1色決めて統一する
- 図には必ずキャプションを付ける。AI検索は画像を読まないが、キャプションは読みます
- ファイル名とalt属性に、図の内容を日本語で書く

**実務ノート**

- 図は任意。無理に作らない
- アイキャッチは、記事タイトルを流し込む**共通テンプレートを1つ作って使い回す**。1本ずつ作ると日次が回りません

**生成ツールの使い分け**

- Recraft: 構造図・ダイアグラム。ベクター出力できるので後から文字を直せる
- ChatGPT / Claude: 図の構造案を出す、SVGを直接書かせる
- アイキャッチ: Canvaなどのテンプレート機能で十分。生成AIを使わない方が速い
