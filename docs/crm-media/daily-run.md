# Revenue CRMの記事を毎朝公開する手順

## 目的と優先順位

法人営業1本、スクール1本を、それぞれ日本語・英語のセットで公開する。現在使える機能を読者の困りごとにつなげる。一般論だけの記事は出さない。本文の型・frontmatter・文体はREADMEと既刊に従う。本人の声の基準は `~/Claude/_config/roles/seiko.md` を最初に読む。

## 毎回の実行

1. 開始と実行環境を報告。CRMとサイトの最新mainを確認する。他の未コミット作業は変更・一括追加しない。作業中のブランチを製品の最新コードと取り違えない。古いクラウド専用ツールやMacのマウントパスを必須にしない。
2. サイトの `src/data/crm-updates.ts` を読み、対象エディション・根拠PR・既刊を照合する。次に最新CRMの画面・ヘルプ・docsを探す。新しいコード変更が無くても、既存機能の未紹介の使い方を探す。パスが無ければ実在するツリーから検索する。
3. B2B記事はREADMEの `b2b_categories`（スタートアップ・中小企業／受託開発・制作／コンサル・マーケティング支援／代理店）を本文と最新実装に合わせて1つ以上選び、日英で揃える。複数指定可。学校には付けない。各segmentで、困りごと、使う機能、具体的操作、根拠ファイル、既刊との違いを記録して選ぶ。過去の保留は現在のコードで再検証。記事の核心に無関係な周辺機能の不足で丸ごと保留にしない。
4. このチャットのCodexが日英の原稿を執筆する。場面→損失→具体的な画面と操作→最初の一歩→本文末CTAを1回。日本語1,200〜1,800字が目安。数字・体験・出典を捏造しない。匿名化し、導入社数・実顧客名・「AI搭載」・「ノマド」・エムダッシュは使わない。英語は読者向けに書き直す。
5. 記事に合う実画面を既存画像かデモで確認する。デモは閲覧と撮影だけ。メール登録・送信・同期・設定変更をしない。認証済みデモのURLを使い、/demosにメールを送信しない。ブラウザが使えなければREADMEの画像なし公開の例外と理由を記録する。PCのタブや個人情報を画像に含めない。
6. Recraftの指定プロジェクトでログイン済みなら場面の写真を生成する。人物はJapanese、明るい室内、読める文字やロゴなし。2026-11-10のユーザー指定に従い、表紙は文字を重ねない場面写真を使う。Recraftが未ログイン・プロジェクトの権限不足・生成不可ならimagegenで生成。既存の写真と並べ、暖かい色味、柔らかい自然光、余白のある少し引いた構図を確認する。写真生成がすべて使えない場合のみ、既存スクリプト `node scripts/generate-eyecatches.mjs <slug>` で文字SVGを生成し、理由を報告する。生成方法とプロンプトを記録。
7. 執筆したCodexが、日英4本と一次情報（CRMの実装の場所、記事のsources、公開ページ）を、実際のClaude Code CLIへ自動で引き渡す。Claudeが [記事の品質チェックリスト（統合版）](article-quality-checklist.md) に沿って①事実検証→②編集レビュー→③校正・推敲を行い、事実・読者・重複・禁止事項・画像との整合を確かめ、結果をこのチャットへ返す。2026-11-20の代表指示により、事実誤認・説明不足・表記などの品質指摘はCodexが修正し、Claudeで再確認してから公開・更新まで進める。都度の承認では止めない。重大な未解決が残る記事は公開しない。
   - レビューはClaude Code CLIが行う。Codexだけの自己レビューや、別のCodexサブエージェントをClaudeの代わりにしない。
   - Claudeの実行が失敗した、または結果が返らなかった記事は「未レビュー」として扱い、そのまま報告する。レビュー済みと装わない。未レビューの記事は公開しない。
   - 執筆→Claudeのチェック→Codexによる修正→Claudeの再チェック→公開・既刊更新まで自動で回す。指摘と修正を記録し、修正前後を区別する。
   - 工程は ①事実検証（領域1・6）→ ②編集レビュー（2・3・5）→ ③校正・推敲（4・6）の順。英語版は4を自然な英語の基準に置き換え、翻訳調・日本語版との事実の差・読者への適合も見る。
   - 指摘には、原文の短い引用・理由・根拠・重大度（Critical＝公開不可／Major＝修正推奨／Minor＝改善任意）・修正案を付ける。問題がなければ「問題なし」、確認できなければ「要確認」と書き、両者を混同しない。
   - 公開してよいのは、未解決の Critical・Major が0件の記事だけ。「要確認」の事実は、確認できるまで本文で断定しない。
   - 代表は2026-11-20に「こうした場合に、修正して更新してほしい」と指示済み。未公開・公開済みの事実訂正、制約・操作説明の補足、校正、根拠に合わせた構成修正はこの承認の範囲として進める。筆者の見解の変更や根拠のない新たな主張は足さない。Critical・Majorが残る場合や事実を確認できない場合は公開を止め、具体的な理由を報告する。
   - 工程4の新規執筆、レビューの指摘、修正、再レビューは別々に記録する。修正後は実際のClaudeで確認し、未解決Critical・Majorが0件になったことを確かめる。
   - 結果は `reviews/<公開日>-<内容>.md` に記録し、当日の `runs/<日付>.md` にそのファイル名と公開判定を書く。
8. `npm ci` と `npm run build`。4つのdist記事HTML、画像、CTA、日付、日英URLを確認する。変更ファイルだけを明示して1コミットにまとめる。最新mainとの差分を確認してから `git push origin HEAD:main`。CRMへのpushはしない。
9. 5分を上限に4記事のHTTP 200と記事タイトルを確認する。push成功と公開成功を混同しない。サイトの配信が失敗したら原因を調べ、自分の変更が原因なら直す。
10. 結果は1通。公開URL、画像の状態、レビュー修正、公開できなかった理由を短く報告。開始・トピック決定・執筆・レビュー・ビルド・push・公開確認の節目にも進捗を出す。

毎日新しい記事を保証するために機能や効果を作らない。出せない場合は調べた候補と成立しなかった具体的理由を残す。「候補が尽きた」とだけ報告しない。
