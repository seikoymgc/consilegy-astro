# 収益診断を「市場調査の計測器」にする設計

最終更新: 2026-06-16
対象: `consilegy-astro` 診断フロー / データ蓄積（MVPはスプレッドシート）
目的: 要件定義 目的③「共通の漏れパターンを蓄積 → 将来のAIダッシュボード/CRMの種」を、**実際にプロダクト要件へ変換できるデータ**として取る。

現状: 蓄積されるのは回答スコアとリード情報のみ。これでは「誰が・どの規模で・どのツールを使っていて・どの漏れに・いくら払う気があるか」が分からず、プロダクトの種にならない。

設計原則: **完了率を守る**。設問（12問）は増やさない。追加データは①メール取得フォーム（既に本気度が高い）と②結果ページ（価値提供後・任意）に置く。

---

## 1. 何を市場調査として取りたいのか（リサーチ・クエスチョン）

プロダクト判断のために、蓄積データから次を答えられるようにする。

| # | 問い | プロダクト上の意味 |
|---|---|---|
| RQ1 | **どのセグメント（規模×業種）に、どの漏れパターンが多いか** | 最初に狙う市場の特定 |
| RQ2 | **どのカテゴリが同時に漏れるか（共起）** | 9パターン仮説の実証・統合。ダッシュボードの初期ビューの優先順位 |
| RQ3 | **どのツール環境で、どの漏れが起きるか** | 連携先（HubSpot/SFDC/kintone…）と置換機会（Excel戻り層） |
| RQ4 | **どの漏れ型が有料診断に転換するか** | 痛み × 支払い意欲。プロダクトを載せる問題の選定 |
| RQ5 | **自動可視化ダッシュボードへの需要** | プロダクト仮説の直接検証（買う人がいるか） |
| RQ6 | **買い手が痛みを語る言葉・きっかけ** | メッセージング・UIコピー・課題定義の素材 |

## 2. 追加で取得するデータ（どこで・なぜ）

### A. メール取得フォーム（[3]）に足す ── セグメント軸
リードが本気で送る画面。選択式で摩擦を最小化。

| 項目 | 形式 | RQ | 備考 |
|---|---|---|---|
| 従業員規模 | 単一選択（〜50/51-100/101-300/301-1000/1001+） | RQ1 | **任意→実質必須化**（分析の主軸。無いと全スライスが死ぬ） |
| 業種 | 単一選択（SaaS・IT / 製造 / 商社・卸 / 専門サービス / 小売・EC / その他） | RQ1 | |
| 使っているツール | 複数選択（HubSpot / Salesforce / kintone / Zoho / MA各種 / BI / Excel・スプレッドシートのみ / 無い） | RQ3 | プロダクトの連携・置換戦略に直結 |
| 役職 | 既存（氏名等と一緒） | RQ4 | 既存項目 |

### B. 結果ページ（[4]）に足す ── 需要と言葉（任意・価値提供後）
漏れマップを見た**痛みのピーク**で聞く。任意なので完了率に効かない。

| 項目 | 形式 | RQ | コピー例 |
|---|---|---|---|
| ダッシュボード需要プローブ | 単一選択 | RQ5 | 「この漏れを**毎月自動で可視化**できるなら使いたいですか？」→ 使いたい / 条件次第 / いまは不要 |
| きっかけ／一番の困りごと | 自由記述（任意・1行） | RQ6 | 「いま一番困っていることを一言で（任意）」 |

> Bは「答えると有料診断の文脈が深まる」フレームにすると回収率が上がる。例:「①②に答えていただくと、診断当日により具体的にお話しできます」。

## 3. 蓄積するレコード設計（スプレッドシート1行＝1診断）

MVPはGAS/フォーム→スプレッドシート。**生の指紋を全部残す**（後から再分析できる形に）。

```
timestamp
# リード
name, company, role, email, consent
# セグメント（A）
employee_size, industry, tools[]   ← tools はカンマ区切り
# 漏れ指紋（最重要・全部残す）
q1..q12              ← 各設問の生スコア 0/1/2（12列）
cat_handoff, cat_dependence, cat_stages, cat_silos, cat_adoption, cat_expansion  ← カテゴリ0-4
total               ← 0-24
band                ← 健全/注意/要改善
pattern_id          ← P1..P9（§前ドキュメントの掛け合わせ型）
worst_category
# 需要・言葉（B）
demand_probe        ← 使いたい/条件次第/不要
pain_text           ← 自由記述
# 転換（GA4と突合 or 手動）
cta_action          ← book / contact / none
booked, won         ← 後追いで埋める
```

ポイント: **q1..q12の生値を必ず残す**。カテゴリ集計だけだと共起分析（RQ2）も設問の弁別力分析もできなくなる。

## 4. GA4イベントに乗せるパラメータ

既存イベント（要件定義 §8）に下記を付与し、行動データ側でもスライスできるように。

| イベント | 追加パラメータ |
|---|---|
| `result_view` | `pattern_id`, `band`, `employee_size`, `industry` |
| `lead_submit` | `employee_size`, `industry`, `tools_count` |
| `cta_book_click` | `pattern_id`, `band` |

→ スプレッドシート（深い分析）とGA4（ファネル・転換）の二系統で同じ軸が揃う。

## 5. 分析レイヤー（蓄積後に回す定番レポート）

| レポート | 作り方 | 答えるRQ |
|---|---|---|
| **セグメント×パターン ヒートマップ** | 規模×業種 を行、pattern_id を列、件数で塗る | RQ1 |
| **カテゴリ共起マトリクス** | 6×6、赤同士の同時出現率 | RQ2（9パターンの実証・統合） |
| **ツール×漏れ** | tools別に各カテゴリ平均スコア | RQ3 |
| **パターン別 転換率** | pattern_id別の book率・won率 | RQ4 |
| **需要プローブ クロス** | demand_probe × pattern × 規模 | RQ5 |
| **設問の弁別力** | 各qの回答分散・カテゴリ判定への寄与 | 設問の刈り込み |
| **痛みの言葉 集約** | pain_text を頻出語/テーマで分類 | RQ6（コピー素材） |

レビュー閾値の目安: **n≥30で傾向、n≥80でセグメント別**を見始める。それ未満は「眺める」だけにして仮説を固定しない。

---

## 6. これが何になるか（プロダクトへの橋）

蓄積が進むと、次が**データで**言える状態になる:

- 「**100-300名・SaaS**で最も多い漏れは**forecast不全（P3）**で、うち◯%が有料診断に転換した」→ 最初のプロダクトはP3を自動可視化するダッシュボード、初期ターゲットはこのセグメント。
- 「Excel戻り層（⑤非定着・赤）の◯%が需要プローブで"使いたい"」→ kintone/SFDC連携より先に**Excel置換**から入る、等。

= 収益診断そのものが、AIダッシュボード/CRMの**ターゲット・初期機能・連携優先度を決める一次調査**になる。

---

## 7. スコープ / 注意
- 設問12問は不変。追加はフォーム（選択式）と結果ページ（任意）のみ。完了率を最優先で守る。
- 個人情報: tools・規模・業種・自由記述の取得目的を同意文に追記（要件定義 §5.3）。
- 自由記述は最小限（1行・任意）。長文は完了率を落とす。
- en版にも同項目を用意（英語リード=外資VP層は規模・ツールの粒度が日本と違うので、業種選択肢は別立てを検討）。
